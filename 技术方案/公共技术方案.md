# 近传 · 公共技术方案

近传首版交付 Android APK 和 Windows 单文件 EXE。主项目同时包含 macOS、iOS/iPadOS 和 HarmonyOS 工程。Windows、Android、macOS 和 iOS/iPadOS 共用 Flutter 页面与 Dart 收发核心，HarmonyOS 使用原生 ArkTS 和 ArkUI，通过同一 v1 协议与其余平台互传。应用运行时无需账号、服务器或互联网。 [产品设计](../产品设计.md)

## 工程分工

| 位置 | 职责 |
| --- | --- |
| `lib/` | 共用收发页面、设备列表、会话状态、发现接口、HTTPS 客户端与监听端、流式传输、SHA-256 和传输记录。根据屏幕宽度调整布局。 |
| `android/` | 系统文件选择器、URI 流、公共 Downloads、局域网权限及 Kotlin 桥接。 [Android 开发方案](Android开发方案.md) |
| `windows/` | 系统选择和拖拽、Downloads 已知目录、文件提交、定位及 Win32 桥接。 [Windows 开发方案](Windows开发方案.md) |
| `macos/` | AppKit 文件选择器、Downloads、访达定位及安全作用域书签。 [macOS 开发与验收](macOS开发与验收.md) |
| `ios/` | iPhone 和 iPad 的 Runner 工程、选档、局域网权限、预览和导出。 [iOS 开发与验收](iOS开发与验收.md) |
| `harmonyos/` | DevEco Studio 原生工程、ArkUI 界面、Network Kit 发现与 TLS 收发、文件授权和保存。 [HarmonyOS 开发与验收](HarmonyOS开发与验收.md) |
| `test/`、`tool/` | Flutter 和鸿蒙主机测试、Dart 测试端及构建脚本。 |

平台层提供文件选择、读流、创建临时接收项、提交、回滚和打开位置等能力。Flutter 端由共享层控制会话和进度，按需读写数据块。每端本地保存设备密钥和成功往来的证书指纹。Windows、Android 和 macOS 接收至系统 Downloads，iOS/iPadOS 接收至「文件」App 的「近传 › Received」，HarmonyOS 接收至经系统授权的下载应用目录。

## 发现和身份

- 用 mDNS/DNS-SD 发布和查找同一服务类型，例如 `_neartransfer._tcp.local.`。监听端启动成功后才发布。广播仅包含协议主版本、显示名、设备指纹和服务端口等发现信息。在线列表跟随服务发现、失联与网络变化，按设备指纹去重并过滤自己。历史记录只给在线设备加「传过文件」标记。
- 首先验证 [Bonsoir](https://pub.dev/packages/bonsoir) 能否在 Android 和 Windows 上双向发布、解析和移除同一服务，并取得正确的局域网地址。验证失败时保留共享发现接口，仅替换相应平台的实现。把 HTTPS 连接失败、局域网权限缺失和设备离线转成可操作的提示。
- 每次安装生成并保存独立的自签名 TLS 证书和私钥，以证书 SHA-256 指纹作为设备 ID。客户端在发送请求前核对实际 TLS 证书指纹。局域网连接直连对端，禁用重定向和系统代理。证书变化时中止连接，不自动覆盖旧记录。TLS 和密钥操作使用成熟库及 Dart 的 [SecurityContext](https://api.dart.dev/dart-io/SecurityContext-class.html)。
- 首版建议采用首次信任（TOFU）。第一次以发现时的指纹约束 TLS 连接，传输成功后固定双方已核验的指纹。此方案维持现有「接受或拒绝」流程，能保护传输免受被动窃听并识别已记录设备的证书变化，首次发现仍可能被同网主动攻击者冒充。如果产品要求首次连接也防冒充，应在既有接收确认中增加两端短码核对，再完成首次信任。
- 接收端显示确认前，按收到请求的来源地址与可发现的发送端服务核对端口和指纹，再用 HTTPS 向该端点验证本次请求 ID。发送端只确认自己正在发出的请求。接收端据此校验发送端持有发现记录对应的证书，并用该身份保存「传过文件」记录。设备名用于显示，不能充当身份。

## 收发协议 v1

每台 App 同时具备 HTTPS 客户端和接收监听端。控制消息用 UTF-8 JSON，文件用原始字节流。请求清单包含随机请求 ID、发送端显示信息，以及每个文件的随机 ID、名称和字节数。两端支持中文文件名、空文件和超过 2 GiB 的文件，大小与进度使用 64 位整数。首版逐个发送文件，任一时刻只处理一个文件流。

| 操作 | 行为 |
| --- | --- |
| `POST /v1/offers` | 提交清单，返回会话 ID 和状态。重复提交同一请求 ID 时返回原会话。接收端验证后显示确认。 |
| `POST /v1/verify-offer` | 接收端向发送端核对随机请求 ID 与本次连接对应的接收端指纹。只返回该请求是否存在并匹配。 |
| `GET /v1/transfers/{id}` | 发送端查询等待、接受、拒绝、取消、超时及每个文件的提交状态。会话 ID 使用不可猜测的随机值，仅通过 TLS 返回。接受后，状态响应附带仅用于本次会话的上传令牌。 |
| `PUT /v1/transfers/{id}/files/{fileId}` | 接受后凭令牌上传对应文件。请求头含声明长度和 SHA-256。接收端验证会话、文件 ID 和请求头后才打开临时目标。校验实际长度和摘要并提交后返回成功。 |
| `POST /v1/transfers/{id}/cancel` | 发送端通知取消。接收端也可在本地取消，双方通过中止连接及查询状态获知结果。 |

会话从等待确认进入接受、拒绝、取消或超时。只有接受状态允许上传。文件状态为待上传、上传中、已提交或失败。所有文件处理结束后，会话汇总为完成、部分完成或失败。取消和文件提交按同一会话顺序处理，已提交项保留，取消先发生时停止提交。

发送端在接收方接受后，先流式计算当前文件 SHA-256，再重新打开文件流上传。两遍读取便于保持协议简单，且不会把整个视频读入内存。接收端边写边计算摘要。清单、等待时间、空闲连接和正在处理的请求数应有明确上限。记录错误类型和任务状态，日志避开私钥、上传令牌和文件内容。

单文件提交成功后，接收端保留最终文件。断网、取消、写入失败或摘要不符时，只清理该会话中未提交的临时项。连接恢复后先查询提交状态，避免把确认响应丢失误判为文件没到。相同会话与文件 ID 已提交时返回原结果；同一 ID 的并发上传只允许一个写入。用户点「重试失败项」时用剩余清单发新请求，再由对方确认。对端进程退出且无法确认结果时，界面显示结果未知，由用户核对后重试。首版支持逐文件重试，断点续传按产品设计留在后续。

接收端只接受单个文件名，按平台规则处理不安全字符和保留名，并确保目标位于下载位置内。保留可用扩展名，同名按「文件 (1).扩展名」递增，提交时防止覆盖现有文件。传输进度按已读写字节展示，单文件显示成功以接收端提交结果为准。接收端在提交首个文件后更新历史记录，发送端在收到首个提交回执或通过状态查询确认后更新历史记录。

## 开发顺序与联合验收

1. **公共基础。** 建 Flutter 工程、共享接口和测试对端。先在同机用临时文件打通发现之外的 HTTPS 请求、接收确认、上传、提交和取消，再验证两台机器上可发现。通过后确定协议字段与错误码，供两端实现。
2. **Windows App。** 先把 Windows 端做成可独立验证的第一个 App，对接测试端验证选取和拖拽、Downloads、进度和单文件 EXE。详见 [Windows 开发方案](Windows开发方案.md)。
3. **Android App。** 按同一协议接入系统选择器、Downloads 和权限。先用测试端分别验收发送和接收，再对接 Windows App。详见 [Android 开发方案](Android开发方案.md)。
4. **联合验收。** 在同一局域网关闭外网连接，保留局域网。使用 Windows 发行 EXE 与 Android 签名 APK，实测两个方向。

| 联合测试 | 通过条件 |
| --- | --- |
| 自动发现与历史 | 打开两端后出现可接收设备，退出后离线设备移出列表。完成一次传输后重开 App，在线旧设备显示「传过文件」。 |
| 逐次确认与拒绝 | 等待确认时无文件正文请求。拒绝后无新文件或临时项。重试会产生新请求并再次等待确认。 |
| 文件完整性 | 双向传输单文件、一批照片和大视频。中文名正常显示，同名文件各自保留。对比源文件与落盘文件的 SHA-256。 |
| 中断与恢复 | 在第二个文件上传中断网或取消，第一个文件保留、第二个临时项清理。恢复后只重试未提交项。模拟提交后响应丢失，查询应找到已提交结果。 |
| 失败反馈 | 模拟证书变化、存储不足、发现不到设备和入站连接受阻，页面显示对应原因和可执行的下一步。 |

两端示例构建用于验证开发环境。首版交付以正式 App 的平台验收和以上真机互传结果为准。
